## Tier 1 — Correctness bugs (1–3 days each)

Ordered by blast radius. Every one of these was silent — the run looked successful. **All eleven are now fixed** (2026-07-30 unless noted); each entry keeps the original diagnosis and records what changed and which test pins it.

1. ~~**`--only` silently applies a cap of 150.**~~ ✅ **Fixed 2026-07-29.** `unlimited_caps=True` → `Pipeline` passes `caps=None` → `analysis.py` fell through to `cap_total = 150`, which then also became the reranker's `top_k`. `caps is None` now takes the same branch as `no_cap` and the `-1` sentinel. Pinned by `tests/test_analysis.py::TestCapEffect` (the *effect*, not the call). **[V]**
2. ~~**LLM extraction blocks the Flet event loop.**~~ ✅ **Fixed.** `extract_events_llm` is the slowest stage (classifier + cross-encoder + N batched LLM calls) and was called directly inside `async def run`, so the UI froze for its whole duration and Pause/Stop could not be delivered — which is why Stop reported "Stopped" while the run continued. Now `await asyncio.to_thread(...)`. Doing this *required* item 3 first: moving a stage that communicated through module-level function attributes onto another thread would have made the race worse. **[V]**
3. ~~**Cross-thread read of a function attribute.**~~ ✅ **Fixed** (with Tier 2.1). `_parse_event_ini` wrote `._last_dropped` and the caller read it on the *next statement*, while up to 5 pool workers called it concurrently — one batch could read a sibling's dropped list. `_parse_event_ini` now returns `(summary, events, dropped)`. Pinned by `TestParseEventIniIsThreadSafe`, including a 20-call/5-thread interleaving test. **[V]**
4. ~~**Approve marks approved even when TickTick failed.**~~ ✅ **Fixed.** The worst bug in the set: `_on_approve`'s `except` block *explicitly* set `_status = "approved"` and wrote an approved fingerprint, so a failed sync permanently hid an event that was never created — lost from both systems at once, silently. `_on_approve_all` had the same defect by fall-through. Both now route through `_sync_one_to_ticktick`, which reports failure; on failure the event stays `new` and the UI logs why. `create_ticktick_tasks` also grew a `failed` bucket, because it catches per-task errors internally and *returning* was never evidence of success. Pinned by `tests/test_ticktick.py::TestFailureReporting`. **[V]**
5. ~~**Reject buckets are read from the wrong backend.**~~ ✅ **Fixed** (with 2.1). The orchestrator read `_extract_events_cloud`'s attributes unconditionally, so a `backend="local"` run reported the cloud path's leftovers or nothing. Buckets now ride back on `ExtractionResult` from whichever backend ran; `_extract_events_local` produces them too (it previously produced none). Pinned by `TestRejectsComeFromTheBackendThatRan`. **[V]**
6. ~~**The shipped `no-web` profile does not disable web.**~~ ✅ **Fixed** — and it was worse than reported. When a name filter matched nothing, `web_kw["sources"]` was simply never assigned, and `fetch_web_sources(sources=None)` means *load them all*. So `no-web` ran a full web harvest, **and so did any typo'd `--web-source`**. The filter result is now assigned even when empty. Pinned by `tests/test_harvest_async.py::TestWebSourceFilter`. **[V]**
7. ~~**CLI-approved events never register as approved.**~~ ✅ **Fixed.** `create_ticktick_tasks` saved fingerprints with the default `status="auto"`, which `find_acted_fingerprint` ignores, so every CLI-synced event came back tagged `new` next run. Now `status="approved"` on both the create and update paths. **[V]**
8. ~~**`chromium_cache.py` raises `NameError`.**~~ ✅ **Fixed.** `gzip_event_score` / `gzip_threshold` are defined nowhere in the module; the raise was swallowed by a bare `except Exception: continue`, so *every* HTML page failed extraction and the path had never once worked. Now uses the same `is_readable_text` gate as the JSON branch 25 lines above. Module still has no production callers (2.4). **[V]**
9. ~~**CWD-relative data paths.**~~ ✅ **Fixed.** `FINGERPRINT_FILE` and `mcp_server.DATA_DIR` were bare `data/` paths, so the stdio MCP server — launched by whatever client spawns it — used a different fingerprint store and event cache than the CLI. Both now anchor to a single `utils.REPO_ROOT`/`data_path()`, which also replaces the hand-counted `.parents[N]` derivations. That counting error had already shipped twice (the classifier dir, then the message cache landing in `src/data/`); it is now computed once, in one place. **[V]**
10. ~~**`RyzenSession._recv()` blocks forever.**~~ ✅ **Fixed.** `readline()` had no timeout, so only a *clean* worker exit was recoverable; an alive-but-wedged worker hung `chat_completion(backend="local")` indefinitely. Now bounded by `io_timeout_s` (default 600s, generous because first-run NPU compilation is slow), after which the worker is killed — a session whose reply was abandoned is desynchronised. The read runs on an explicit **daemon** thread, not a `ThreadPoolExecutor`: pool threads are non-daemon and joined at interpreter exit, so abandoning a blocked `readline` there hangs shutdown instead of the call. (Caught by the test suite hanging.) Pinned by `tests/test_interlock.py`. **[V]**
11. ~~**`web_modes/feed.py` tags messages with the source name.**~~ ✅ **Fixed.** Emitted `"platform": "instagram"` instead of `"web"`, violating `EH-STD-MSG-v0`, so `CapConfig.get("instagram")` fell through to a default and the `web` cap never applied to feed sources. All three sites now emit `"web"`; the source name moved to `channel`. **The existing test did not catch this** because it passed `"web"` as the argument production was getting wrong — it now passes a real source name. **[V]**
